# Тестирование Timer 3

## Цели

Тесты должны защищать поведение таймера и настроек, не зависеть от реального аудиоустройства и оставаться быстрыми. Проект использует преимущественно unit- и компонентные тесты с лёгкими fake-объектами для Qt-виджетов.

Снимок на 18 июля 2026 года:

- 165 успешно проходящих тестовых сценариев;
- 82% общего покрытия строк;
- наиболее важные модули model, context, clock, tunes_controller и конфигураторы покрыты полностью или почти полностью.

Числа являются ориентиром, а не жёстким контрактом. При изменении кода важнее сохранить проверки критических ветвей, чем искусственно поддерживать процент.

## Быстрый запуск

    run_tests.bat

Эквивалентная команда:

    .venv\Scripts\python.exe -m pytest -q tests --basetemp=.pytest_tmp

Параметр basetemp удерживает временные файлы внутри проекта и делает запуск предсказуемым в ограниченных Windows-окружениях.

## Покрытие

Установите Coverage.py:

    .venv\Scripts\python.exe -m pip install coverage

Текстовый отчёт:

    .venv\Scripts\python.exe -m coverage run --source=timer_3 -m pytest
    .venv\Scripts\python.exe -m coverage report -m

HTML-отчёт:

    .venv\Scripts\python.exe -m coverage html
    start htmlcov\index.html

Разумная цель проекта:

- не ниже 80% для всего пакета;
- 90% и выше для чистой бизнес-логики;
- обязательное покрытие каждой исправленной регрессии.

main.py и отладочная функция печати Tab-порядка имеют меньший приоритет, чем обработка завершения таймера, повторов цикла и ошибок профиля.

## Устройство набора тестов

### Таймер

- test_clock.py — порядок событий тика и завершения, запуск, остановка и callback-ошибки;
- test_precise_timer.py — сброс состояния и компенсация положительного/отрицательного дрейфа;
- test_timer_controller.py — отображение времени, границы голосовых и звуковых событий, интервалы и повторы цикла;
- test_inform.py — голосовой Lock, финальная мелодия и ошибки аудио.

### Настройки

- test_tunes_defaults.py — согласованность значений по умолчанию;
- test_tunes_mapper.py и test_tunes_mapper_extra.py — JSON, DTO и Model;
- test_tunes_model.py, test_tunes_model_extra.py и test_model_complete.py — изменение всех поддерживаемых полей и режим времени;
- test_tunes_storage.py и test_storage_errors.py — чтение, запись, переключение профилей и файловые ошибки;
- test_context.py — координация Model и Storage.

### Интерфейсная логика

- test_focus_transition.py — схемы фокуса и выбор начального виджета;
- test_configurators.py — валидаторы, начальное состояние и связи Qt-сигналов;
- test_tunes_controller.py — обработчики окна настроек и предупреждения.

Эти тесты проверяют UI-логику без показа реальных окон. Полный пользовательский сценарий и аудио остаются предметом ручного smoke-теста.

## Изоляция внешних зависимостей

### Файловая система

Используйте pytest fixture tmp_path. Не создавайте тестовые JSON-файлы в корне репозитория и не обращайтесь к реальному %APPDATA% пользователя.

Если тест создаёт Storage без явного app_dir, переменная APPDATA должна быть перенаправлена через monkeypatch.

### Qt

Для контроллеров и конфигураторов используйте минимальные fake-виджеты, реализующие только нужные методы и сигналы. Это ускоряет тесты и позволяет точно проверять переданные значения.

Реальный QApplication нужен только для поведения, которое невозможно корректно воспроизвести fake-объектом.

Для headless-запуска можно задать:

    set QT_QPA_PLATFORM=offscreen

### Аудио

В тестах запрещено воспроизводить реальный звук. Подменяются:

- pygame.init и pygame.mixer;
- pyttsx3.init;
- QApplication.beep;
- QTimer, ожидающий завершение мелодии.

Для headless pygame можно использовать:

    set SDL_AUDIODRIVER=dummy
    set PYGAME_HIDE_SUPPORT_PROMPT=1

## Как добавить тест регрессии

1. Воспроизведите неправильное поведение на минимальном объекте.
2. Сформулируйте ожидаемый результат через публично наблюдаемое состояние.
3. Подмените только внешние эффекты: звук, выход приложения, файловую систему или Qt event loop.
4. Убедитесь, что тест падает без исправления.
5. Исправьте код минимально.
6. Запустите новый тест, полный pytest и Ruff.
7. Проверьте, что тест не зависит от порядка запуска.

Пример критической регрессии циклического режима: число повторов должно уменьшаться до проверки завершения. Иначе после последнего полного цикла может ошибочно запускаться дополнительный цикл.

## Требования к качеству теста

Хороший тест:

- отражает пользовательский или архитектурный контракт;
- имеет одно понятное основание для падения;
- не требует sleep;
- не зависит от реального времени и звука;
- создаёт данные внутри tmp_path;
- не изменяет глобальные настройки пользователя;
- проверяет результат, а не внутреннюю последовательность вызовов без необходимости.

Параметризация уместна для диапазонов, форм слов и однотипных ключей модели. Не объединяйте разные пользовательские сценарии в один чрезмерно большой тест.
